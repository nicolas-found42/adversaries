# Procedural council sculpture: Rust tool research

Researched 2026-11-03. Scope: a sculptural, high-fidelity 3D council visualization inside an existing egui/eframe 0.37 Glow interface, on native and WASM. This is source research, not a tested integration or a claim that any library is newly released or undiscovered.

## Recommendation

Combine **fast-surface-nets 0.2.1** for organic implicit geometry, **noise 0.9.0** for seeded material/shape variation, and **three-d 0.19.0** for depth-tested GPU rendering and physical materials. Treat this as a proposed stack pending a callback proof of integration. An egui `Mesh` with projected triangles and CPU lighting is a useful low-risk fallback, but its 2D vertices have no depth component: sorting triangles cannot guarantee correct visibility for intersecting, concave sculpture. High visual fidelity favors a real 3D pass. [egui Vertex](https://docs.rs/epaint/0.37.0/epaint/struct.Vertex.html), [three-d renderer](https://github.com/asny/three-d#structure).

Discovery provenance is concrete: [stevinz/awesome-game-engine-dev](https://github.com/stevinz/awesome-game-engine-dev) lists three-d as a renderer, and [uhub/awesome-rust](https://github.com/uhub/awesome-rust) lists three-d and glam. Following the renderer's own noise example dependency and searching implicit meshing upstream led to noise-rs and fast-surface-nets. **Do not claim that fast-surface-nets itself was found in those lists.** The interesting combination is the mesh generator plus a compact renderer, rather than a popularity ranking. [three-d manifest](https://docs.rs/crate/three-d/0.19.0/source/Cargo.toml.orig), [fast-surface-nets upstream](https://github.com/bonsairobo/fast-surface-nets-rs).

## Verified tools and interfaces

| Tool | Verified release / license | Useful interface and role | Tradeoff |
| --- | --- | --- | --- |
| fast-surface-nets | 0.2.1; MIT OR Apache-2.0 | `surface_nets(&sdf, &shape, min, max, &mut SurfaceNetsBuffer)` produces indexed geometry and estimated normals; buffer reuse avoids repeated allocation. | Regular-grid sampling limits detail; Naive Surface Nets averages edge crossings rather than solving sharp-feature Hermite constraints. |
| three-d | 0.19.0; MIT | `Context::from_gl_context(Arc<glow::Context>)`; `Mesh`, `CpuMesh`, `PhysicalMaterial`, `Gm`, `Camera`, and render targets supply the GPU pass. PhysicalMaterial exposes metallic and roughness. | Needs careful shared GL state, framebuffer/depth setup, and viewport management in egui. |
| noise | 0.9.0; Apache-2.0/MIT | `NoiseFn::get`, seeded Perlin/OpenSimplex and fractal combinators provide reproducible variation; default features are empty. | A noise-displaced field is not necessarily an exact signed distance field; keep displacement small for silhouette control and sample adequacy. |
| glam | fast-surface-nets internally uses 0.29; current release queried was 0.34.2; MIT OR Apache-2.0 | The mesher re-exports glam and accepts ordinary array-based API inputs, avoiding a requirement to share math crate versions. | three-d uses cgmath 0.18: convert at the mesh boundary rather than assuming common vector types. |

## Integration proposal

1. Keep eframe as window/context owner. Add `three-d = { version = "0.19", default-features = false }`; leave its `egui-gui` feature disabled. The released crate's optional egui integration targets **0.34**, not 0.37. Both three-d 0.19 and egui_glow 0.37 use Glow 0.17, so the GL context type is plausibly shareable without a second UI dependency. This is a manifest-based inference, not a successful compile. [three-d manifest](https://docs.rs/crate/three-d/0.19.0/source/Cargo.toml.orig), [egui_glow manifest](https://docs.rs/crate/egui_glow/0.37.0/source/Cargo.toml).
2. Build the renderer once from eframe's GL context. Paint through an `egui_glow::CallbackFn`, using the allocated panel's pixel viewport and clip rectangle. Either provide an offscreen color/depth target or verify the host framebuffer's depth attachment before relying on depth testing. The upstream renderer explicitly allows replacing its window module with eframe and targets OpenGL 3.3 on desktop and WebGL2 in browsers. [three-d support and integration](https://github.com/asny/three-d#structure), [egui callback source](https://docs.rs/crate/egui_glow/0.37.0/source/src/painter.rs).
3. Compose the central sculpture from smooth unions/subtractions of sphere, torus, capsule and rounded-box fields. Separate primary silhouette, structural ribs and subtle erosion. Sample only when model parameters change; rotate the camera/object without remeshing. Convert `SurfaceNetsBuffer` positions/normals/indices into `CpuMesh`; normalize normals explicitly. This is an implementation proposal based on the mesher's output API, not an upstream ready-made modeling system. [SurfaceNetsBuffer](https://docs.rs/fast-surface-nets/0.2.1/fast_surface_nets/struct.SurfaceNetsBuffer.html).
4. Use physical materials for the sculpture and distinct metal/ceramic assignments for council members; let a restrained key/fill/rim setup reveal curvature. Keep topology changes slow and deterministic. Inspect upstream environment/PBR examples for lighting, tone mapping and color handling before implementing those effects. [three-d examples](https://github.com/asny/three-d/tree/master/examples), [PhysicalMaterial source](https://docs.rs/crate/three-d/0.19.0/source/src/renderer/material/physical_material.rs).

## Other leads and exclusions

The awesome Rust list also surfaces **rend3**, but its upstream README announces maintenance mode and it uses wgpu: adopting it would add a rendering-backend migration to this Glow task. It is therefore a poor first integration despite its richer renderer architecture. [awesome list](https://github.com/uhub/awesome-rust), [rend3 upstream](https://github.com/BVE-Reborn/rend3).

**SMesh** is an interesting separate procedural topology lead: its author describes a Surface Mesh abstraction aimed at procedural generation. It is not required for an implicit sculpture, and its operations, current release/license, and WASM behavior were not audited here; do not add it on this note alone. [SMesh upstream](https://github.com/Bendzae/SMesh).

## Runtime unknowns and acceptance evidence

- No native/WASM build, GL callback, GPU screenshot, frame-time benchmark, or Safari check was performed for this research. Verify those before presenting the proposed stack as working.
- Test native startup plus browser WebGL2, resizing/HiDPI, clipping, transparent UI overlays, and correct rendering of an occluded concave shape. Confirm framebuffer restoration and renderer lifetime during shutdown/context loss.
- Measure sampling, meshing, GPU upload and steady-state rendering separately. Upstream mesher throughput figures are an upstream CPU benchmark, not this application's frame rate. Begin with a modest volume, cache geometry, and increase resolution only after silhouette and latency review. [upstream benchmark description](https://github.com/bonsairobo/fast-surface-nets-rs#fast-surface-nets).
- three-d master currently identifies itself as **0.20.0**, while crates.io returned **0.19.0** as the latest published release during this research. Pin published APIs; master examples can drift. [master manifest](https://github.com/asny/three-d/blob/master/Cargo.toml), [published release](https://crates.io/crates/three-d/0.19.0).


## Implemented composition and observed checks

The implementation in `src/ui/sculpture.rs` uses the two-tool core: fast-surface-nets 0.2.1 plus three-d 0.19.0, with three-d defaults disabled. Noise remains a researched option; it is not an installed dependency. Four deterministic 40³ implicit fields produce a fused bloom, softened mineral, twisted loop and rounded tablets. Each uses Cook–Torrance/GGX shading, a distinct roughness/metallic assignment, key/fill/rim lights and a cached shadow map. The pedestal is another closed implicit surface. Models, lights, textures and shader programs are retained on the GL thread; motion changes the camera without resampling the fields.

A fixed 384² offscreen color/depth pair supplies depth even when egui's framebuffer has none. The Glow callback copies only color into egui's viewport and clip rectangle, then relinquishes the borrowed framebuffer without deleting it. Native shutdown drops the studio while the host context is current. This is a bounded decorative renderer, not a modeling editor, path tracer or a claim of physically measured materials. The retained role names and run-state text explain the process independently of the sculpture.

Actual macOS native and Chromium WebGL2 renders were inspected. A native capture showed the same four distinct sculptures, loop opening, lit surfaces and pedestals. The first browser capture exposed an orthographic framing error: three-d scales the view height by camera distance. The corrected framing has a projection regression. A fresh review also reproduced overlapping role names at 150% narrow layout; the crew now switches to two rows below 250 layout points, with a disjoint-label regression covering 150% and 200% equivalents. Geometry tests validate finite indexed meshes, unit normals, two incident faces per mesh edge, closed field boundaries and the loop opening.

A local browser harness exercised 1280-, 390- and 320-pixel widths, compared reduced-motion screenshots across time (pixel-identical), opened/cancelled the composer through shared reading-view actions, and returned to the visual workspace. It observed no page errors, GL warnings or POST requests. A separate REA controlled scenario repeated the wide composer round trip against an isolated server serving the built WASM and empty session/catalog fixtures: all steps completed, no console/page errors, and the owned browser terminated. Validation commands are the complete repository pre-commit suite, `cargo check --target wasm32-unknown-unknown --lib --bin council-ui`, `trunk build --offline`, and the local browser harness. No frame-rate or startup-latency benchmark is claimed; fixed grids/textures and cached geometry establish bounded work, not a measured performance guarantee.
